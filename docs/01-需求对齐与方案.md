## 一、站点探测结论

### 1.1 站点形态

- 技术栈：Next.js（App Router + Turbopack），部署于 openresty，HTTPS 正常，强制 HSTS
- 前端产物：React + Tailwind + shadcn/ui + Ant Design Icons
- 站点身份：开源项目 `markcxx/coco-downloader` 的部署版本（Web 端为单页搜索+下载页）
- 源码上游：`https://github.com/markcxx/coco-downloader`；桌面客户端另有 `markcxx/CoCoMusicRelease`
- **站点自身没有收藏功能**（localStorage 只用于明暗主题）→ APP 的"自建收藏夹"是纯新增能力

### 1.2 环境开关（前端可读，影响下载行为）

```js
window.__COCO_ENV = {
  "ENABLE_DOWNLOAD": "1",           // "0"=关闭本站下载代理，"1"=开启
  "ANNOUNCEMENT_ENABLED": "0",
  "ANNOUNCEMENT_TEXT": "由于本站当前流量包达到上限，下载功能已临时关闭，将为你跳转到原链接。"
}
```

> **关键风险**：官方明确说过"流量包达到上限→临时关闭下载代理"。该开关随时可能翻转。
> APP 必须实现**双通道下载**：优先走 `/api/download`（服务端代理），失败/被关闭时自动回退到 `/api/url` 直链下载。

### 1.3 完整 API 规格（实测）

全部 **无需鉴权**、无 Referer 校验、无 UA 校验、无自定义 Header 要求。

| 接口 | 方法 | 参数 | 返回 |
|---|---|---|---|
| `/api/search` | GET | `q`(必填,缺省返回400 `{"error":"Missing query"}`)、`provider`(默认 `netease`)、`limit`(≤50,超出按50)、`offset` | `{"items":[{...}]}` |
| `/api/url` | GET | `id`(必填)、`provider`(默认 `netease`)、`extra`(可选,JSON字符串) | `{"url","type","bitrate","cover"}` 或 500 `{"error":"Failed to get url"}` |
| `/api/lyric` | GET | `id`、`provider`、`extra` | `{"songid","provider","lines":[{"time":秒(float),"text":str}]}` |
| `/api/download` | GET | `id`、`provider`、`filename`、`extra` | 二进制音频流，`Content-Disposition: attachment` |

**search item 结构**（实测，netease 与 qq 的 extra 字段不同）：

```jsonc
{
  "id": "1406665428",
  "title": "三寸天堂",
  "artist": "陈晶",
  "album": "三寸日光",
  "cover": "http://p3.music.126.net/....jpg",
  "duration": "04:48",          // 字符串 mm:ss
  "provider": "netease",
  "extra": {                    // 解析器/音质上下文，必须原样回传给 /api/url、/api/download
    "cover": "...",
    "selectedLevel": "lossless", // netease 风格
    "selectedFormat": "flac",    // qq 风格
    "selectedParser": "xcvts",   // qq 风格
    "qualityOptions": [
      {"value":"standard","label":"标准音质","quality":"128","format":"mp3"},
      {"value":"exhigh","label":"极高音质","quality":"320","format":"mp3"},
      {"value":"lossless","label":"无损音质","quality":"lossless","format":"flac/mp3"},
      {"value":"hires","label":"Hi-Res","quality":"hires","format":"flac"},
      {"value":"jyeffect","label":"高清环绕声","quality":"jyeffect","format":"flac/mp3"},
      {"value":"sky","label":"沉浸环绕声","quality":"sky","format":"flac/mp3"},
      {"value":"jymaster","label":"超清母带","quality":"jymaster","format":"flac/mp3"}
```

| `bodian` | 波点 | ✅ (返10) | ✅ | 走酷我 CDN |

| `kugou` | 海棠 | ✅ | ❌ 500 | |
| `livepoo` | 力音 | ✅ | ❌ 500 | |
| `gequbao` | 歌曲宝 | ⚠️ 超时 | - | |
| `gequhai` / `bugu` / `qqmp3` / `mitu` / `aiting` / `joox` | 歌曲海/布谷/QQMP3/米兔/爱听/JOOX | ❌ 空结果 | - | |
| `jianbin-netease` / `jianbin-qq` / `jianbin-kugou` / `jianbin-kuwo` | 煎饼-1~4 | ❌ 空结果 | - | |

> **这是本次探测最重要的结论**：单个渠道随时会挂（500/空/超时），且返回条数不符合 `limit`（有的忽略分页，有的封顶 10/20/30）。
> APP **不能把可靠性押在单一渠道上**，必须做多渠道并发搜索 + 失败降级 + 渠道健康度提示。

### 1.5 其他实测细节

- `/api/download` 返回头固定 `content-type: audio/mpeg`（即使内容是 flac）→ APP **不能靠 Content-Type 判断格式**，要靠自己请求的音质/文件名后缀
- 中文文件名通过 RFC 5987 正确编码：`filename*=UTF-8''%E9%99%88%E6%99%B6...` ✅
- 非法 id → 500 `{"error":"Failed to get url"}`（不是 404）
- `/api/url` 返回的 netease 直链带时间戳，**约 30 分钟有效**
- 代理下载体积大（实测单曲 flac/mp3 51MB）→ 必须做后台下载 + 断点续传 + 并发限制

### 1.6 【重要】拉取上游仓库源码后的版本差异发现

我把 `markcxx/coco-downloader` 主分支源码完整拉下来对比，发现**你部署的 m.resound.vip 不是主分支的构建产物**，两者在三个关键点上有分歧：

**① `/api/download` 的返回形态不同（最关键）**

| | 返回形态 | 字节由谁下载 |
|---|---|---|
| 主分支源码 `src/app/api/download/route.ts` | JSON `{url, type, delivery}` | **浏览器**直连该 url 下载 |
| **你的部署版（实测）** | **二进制音频流**（`content-type: audio/mpeg`，`content-disposition: attachment`） | **服务端代理**转发 |

→ APP 的下载逻辑必须**同时兼容两种**：请求 `/api/download` 后嗅探 `Content-Type`，
`application/json` → 取 `url` 再自行下载；`audio/*` / `octet-stream` → 直接把 body 落盘。
你哪天升级了站点，APP 也不用改。

**② 渠道注册表不同**

| | 渠道集合 |
|---|---|
| 主分支（16 个） | `netease` `qq` `kugou` `bodian` `gdstudio-netease` `at38-netease` `at38-qq` `gequhai` `gequke` `qqmp3` `livepoo` `jianbin-netease/qq/kugou/kuwo` |
| **你的部署版（17 个，实测）** | `netease` `qq` `kugou` `bodian` `qqmp3` `gequhai` `livepoo` `migu` `jianbin-*`×4 **+ `gequbao` `bugu` `mitu` `joox` `aiting`** |

主分支新增了 `gdstudio-netease`（GD音乐台）、`at38-netease/qq`（51ape）、`gequke`（歌曲客）三个渠道，
而你部署版保留了 `gequbao`/`bugu`/`mitu`/`joox`/`aiting` 五个主分支已移除的渠道。

→ APP 的渠道列表**以你线上实测的 17 个为准**，但代码里做成"可扩展注册表"，
并内置一个**渠道自检**功能（设置页一键体检每个渠道的搜索+取流），随时发现服务端变更。

**③ 音质档位不同**

主分支 netease 只有 3 档（standard/exhigh/lossless），你的部署版有 **7 档**
（多出 hires / jyeffect / sky / jymaster）。
主分支 netease 取流走 `api.qijieya.cn/meting/`，`extra.selectedLevel` → 码率映射：`standard=128`、`exhigh=320`、`lossless=2000`。
→ APP 必须**动态读取 `extra.qualityOptions` 渲染音质选择器**，不能硬编码。

**④ 其它从源码读到的契约**

- `delivery` 字段有两种：`audio`（可直接下载）与 `source-page`（仅网盘入口，如 `livepoo` 力音）→ 这类渠道 APP 只能"跳转源站"，不能自动下载
- 未知 provider → 主分支返回 `{"error":"该渠道已下架或不存在..."}`；你的部署版返回 500 `{"error":"Failed to get url"}`
- 主分支 `/api/search` 支持 `provider=all`（回落到默认渠道）和 `source` 参数校验（只接受 `channel`）
- 你的部署版默认渠道是 `netease`，主分支默认是 `gdstudio-netease` → APP 任何时候都要**显式传 provider**
- 源码 `download-url.ts` 的安全策略：直链强制升级为 https，拒绝带账号密码/端口/内网主机名的 URL → APP 下载直链时照做，避免 SSRF 类风险
- 源码 `desktop/diagnostics/provider-status-2026-10-11.json` 的实测结论与我自己的探测**高度一致**：netease/qq/kugou/gequhai/bodian/qqmp3/jianbin-* 可用，migu 部分可用，livepoo 不可用

### 1.7 【升级后复测 · 2026-11-04 22:05–22:25】

用户在后端升级后要求复测。结论分三层：

#### ① 应用层（Next.js）**逐字节未变**——升级没有落到 m.resound.vip 的 Web 构建

| 校验项 | 升级前 | 升级后 | 判定 |
|---|---|---|---|
| 首页 HTML | 17,898 B | 17,898 B，`cmp` **完全一致** | 未变 |
| 11 个 JS chunk | — | `cmp` 逐个 **全部 IDENTICAL** | 未变 |
| 前端渠道表 | 17 个旧渠道 | 仍是同样 17 个 | 未变 |
| `/api/download` 形态 | 二进制流 | 仍是二进制流（body 魔数 `fLaC`） | 未变 |
| netease 音质档位 | 7 档 | 仍是 7 档 | 未变 |
| 未知渠道行为 | 回落 netease | 仍回落 netease | 未变 |

主分支的三个特征**一个都没出现**：新增渠道 `gdstudio-netease` / `at38-netease` / `at38-qq` / `gequke`
**全部被静默回落到 netease**（返回项的 `provider` 字段仍是 `netease`）；`/api/download` 仍返回二进制而非 JSON；
`/api/url` 仍返回 `{url,type,bitrate}` 三字段而非主分支的 `{url,type,delivery}`。

> 另发现：主分支 `/api/search` 对 `source != "channel"` 会返回 400，部署版**照单全收**；
> 主分支对未知渠道会抛「该渠道已下架或不存在」，部署版则**静默回落**。
> → 确认线上跑的是**自定义分支**，不是上游 main。APP 必须以线上实测为准，不能照抄上游。

#### ② 上游解析服务的渠道可用性**确有改善**（这是升级的真实收益）

| 渠道 | 首轮探测 | 升级后 | 变化 |
|---|---|---|---|
| `qqmp3`（米兔） | 搜索空 | **搜索50条 + 取流OK + Range 206** | ✅ 已修复 |
| `mitu`（米兔） | 搜索空 | **搜索50条 + 取流OK + Range 206** | ✅ 已修复 |
| `gequbao`（歌曲宝） | 超时/空 | 搜索OK（周杰伦112条），取流仍500 | ⚠️ 部分改善 |
| `bodian`（波点） | OK | OK（+Range 206） | ✅ |
| `migu`（咪咕） | OK | OK（Range 200，不支持续传） | ➖ |
| `netease` | OK | OK（+Range 206） | ✅ |
| `qq` / `kugou` / `livepoo` | 搜索OK取流500 | 仍搜索OK、取流500 | ➖ 未变 |
| `gequhai` / `bugu` / `joox` / `jianbin-*` | 搜索空 | 仍搜索空 | ➖ 未变 |
| `aiting` | 超时 | 仍超时 | ➖ 未变 |

两轮复测结果**完全一致**，非偶发抖动。

#### ③ 【最重要】直链 vs 代理：**下载主路径要反转**

实测同一首歌（51MB flac）：

| 路径 | 速度 | Range 断点续传 | 直链有效期 |
|---|---|---|---|
| `/api/url` → 直链（`m801.music.126.net` / `car-er.kuwo.cn`） | **7.6–64.8 MB/s** | ✅ **206 Partial Content** | **约 30 分钟**（13 分钟后实测 403） |
| `/api/download` → 服务端代理 | 1–10 MB/s（并发时骤降） | ❌ 恒返回 200，不支持续传 | 无所谓（服务端实时代理） |

**v0.1 方案写的是「代理优先、直链兜底」——这个结论是错的，要改成「直链优先、代理兜底」。**

理由：
1. 直链支持 Range → **断点续传可用**；代理不支持 → 代理下载失败必须整包重来
2. 直链快一个数量级，且不占你的服务器流量包（正对应公告里「流量包达到上限」的问题）
3. 直链会过期，所以策略是：**取直链 → 下载 → 403/失效时重新取直链 → 用 Range 续传**，而不是重头下

但**代理仍必须保留**作为兜底：直链过期且重取失败、或渠道只支持代理（`migu` 不支持 Range）时使用。

#### ④ netease 7 档音质的**真实位率**（用户可能误以为母带是真母带）

逐档实测 `/api/url` 返回的 `bitrate`：

| 档位 | 标签 | 实测 type | 实测 bitrate |
|---|---|---|---|
| standard | 标准音质 | mp3 | 128 |
| exhigh | 极高音质 | mp3 | 320 |
| lossless | 无损音质 | flac | 2000 |
| hires | Hi-Res | flac | **2000**（与无损同） |
| jyeffect | 高清环绕声 | flac | **2000** |
| sky | 沉浸环绕声 | flac | **2000** |
| jymaster | 超清母带 | flac | **2000** |

→ 后四档**实际都返回同一个 2000k flac**，并没有真正区分。
→ APP 音质选择器应当**按实测位率显示**，避免标着「超清母带」实际给的是普通无损。UI 上标注真实 bitrate 更诚实。

## 二、技术方案建议

### 2.1 选型：Kotlin + Jetpack Compose（原生）

理由（对比 Flutter / RN / WebView 套壳）：

| 维度 | 原生 Kotlin+Compose | Flutter | RN | WebView 套壳 |
|---|---|---|---|---|
| Media3/ExoPlayer 播放 + 后台 + 通知栏控制 | ✅ 原生一等公民 | ⚠️ 需自研桥接 | ⚠️ 需自研桥接 | ❌ |
| MediaStore 写入音乐库 / 存储权限适配 | ✅ | ⚠️ | ⚠️ | ❌ |
| WorkManager 后台下载 + 断点续传 | ✅ | ⚠️ | ⚠️ | ❌ |
| 包体积 | ~8MB | ~20MB+ | ~15MB+ | ~5MB |
| 开发速度 | 中 | 快 | 中 | 最快 |
| 长期可维护性 | ✅ | ✅ | ⚠️ | ❌ |

APP 强依赖**后台下载、进度通知、MediaStore 写入、系统播放器集成**，这些都是 Android 平台能力，原生是最短路径。

### 2.2 技术栈清单

- **Kotlin 2.0 + Jetpack Compose + Material 3**，单 Activity + Navigation Compose
- **网络**：OkHttp + kotlinx.serialization（或 Retrofit）
- **数据库**：Room（收藏夹、下载任务、播放记录、歌词缓存）
- **播放**：Media3 ExoPlayer（支持 flac/mp3），Service + MediaSession + 通知栏
- **下载**：WorkManager + OkHttp Range 断点续传，进度通知
- **存储**：MediaStore (Android 10+) / 传统路径 (Android 9-) + FileProvider
- **依赖注入**：Hilt（可选，也可手动 ServiceLocator 减复杂度）
- **最低版本**：minSdk 24 (Android 7.0)，targetSdk 34/35

### 2.3 建议目录结构

```
app/
  data/
    remote/   ApiClient, dto (SearchResultDto, UrlDto, LyricDto), ProviderRegistry
    local/    Room: FavoriteEntity, CollectionEntity, DownloadTaskEntity, HistoryEntity
    repo/     MusicRepository, FavoriteRepository, DownloadRepository
  feature/
    home/     搜索页（渠道切换、聚合结果、质量选择）
    player/   播放页（歌词滚动、进度、音质切换）
    favorite/ 收藏夹页（自建歌单管理）
    download/ 下载中心（任务队列、进度、重试）
    setting/  设置页（服务器地址、默认音质、下载策略）
  media/      PlaybackService, MediaSession, NotificationProvider
  download/   DownloadWorker, DownloadManager
  ui/         theme, components
```

### 2.4 关键工程决策

1. **多渠道聚合**：一次搜索并发打多个渠道，按渠道分组展示 or 合并去重（按 title+artist），并显示每个渠道的"可用/失效"状态徽标
2. **直链优先、代理兜底**（v0.2 修订，理由见 §1.7③）：
   - 主路径：`/api/url` 取直链 → 直连 CDN 下载（支持 Range，可断点续传，不占服务器流量）
   - 续传策略：直链 403/过期 → 重新取直链 → 带 `Range` 头从断点续，不整包重下
   - 兜底：`/api/download` 代理（渠道不支持 Range 时、或直链重取失败时）
   - 再兜底：`/api/url` 的 `delivery == "source-page"` → 引导用户去源站
3. **下载文件格式判定**：代理返回的 `Content-Type` 恒为 `audio/mpeg`，即使内容是 flac（实测 body 魔数 `fLaC`）→ **必须按 body 魔数 + `/api/url` 的 `type` 字段判定格式**，不能信 Content-Type
4. **extra 透传**：搜索返回的 `extra` 必须**原样 JSON 化**回传给 `/api/url`、`/api/download`、`/api/lyric`，否则音质降级或取流失败
5. **音质动态渲染 + 真实位率展示**：由 `extra.qualityOptions` 驱动档位列表，但**标注 `/api/url` 实测返回的真实 bitrate**（hires/sky/jymaster 实测均为 2000 flac，不应标成真母带）
6. **渠道白名单 + 回落识别**：线上对未知渠道**静默回落 netease**。APP 收到响应后必须比对 `items[].provider` 与请求的 provider，**不一致就标记为"已回落"**并提示用户，否则用户会以为搜的是 QQ 音乐结果
7. **delivery 分流**：`delivery == "source-page"` 的渠道（如力音）只提供"前往源站"动作，不进自动下载队列
8. **音源地址可配置**：设置页可改 base URL（默认 `https://m.resound.vip`），方便你换服务器
9. **渠道自检**：设置页提供"一键体检"，并发探活所有渠道的搜索+取流+Range，输出健康报告（可用/取流500/搜索空/超时）
10. **失败可观测**：每个渠道的失败原因在 UI 上可见，而不是静默吞掉
11. **直链安全策略**：沿用上游 `directAudioUrl` 规则——强制 https，拒绝内网/带凭据/带端口的 URL
